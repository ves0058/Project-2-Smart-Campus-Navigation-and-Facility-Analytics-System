Name: Rodion Dvoretskii

Description:

Facility: stores facility ID, name, building, and category.

HashTable: implements custom hashing, insertion, deletion, collision handling, and ID lookup.

HashTable Time Complexity: 
	-> Average: O(1) for insertion, deletion, and searching.
	-> Worst: O(n)

HashTable Space Complexity: 
	-> O(n + m), where "n" is the table capacity (101) and "m" is number of stored facilities.

Hash Function: Multiplicative String Hash Function (DJB2) "hash": 
	It processes the string one character at a time, and for each character it performs two operations:

	1. Multiply the current running hash value by a constant.
	2. Add the ASCII (or Unicode) value of the current character to the result.
	
	This is repeated until every character in the string has been processed. Because multiplication happens at every step, 
	a character's position changes how much it influences the final result, which is exactly what prevents anagrams from colliding.

	The most common example is the DJB2 hash function, developed by Daniel J. Bernstein. 
	It uses an initial value of 5381 and a multiplier of 33.
	These specific constants were chosen because, empirically, they produce a 
	good distribution for typical English text and are simple and fast to compute.

Collision Resolution Strategy: Separate Chaining
	The project uses Separate Chaining (also called Open Hashing) to handle collisions. 
	Each bucket stores a collection of facilities using a vector. 
	When multiple facility IDs produce the same hash index, they are stored in the same bucket instead of overwriting existing records.

	This approach was chosen because it allows multiple facilities to share a bucket and does not impose a fixed maximum number of facilities.

	Since the project uses Separate Chaining, the hash table can continue accepting new facilities even when all buckets contain elements. 
	Multiple facilities can be stored in the same bucket.

Initial capacity: 101 (a prime number selected to help distribute elements across the table)

Collision-counting definition: 
	A collision is counted when an accepted facility is inserted into a bucket that already contains at least one facility. 
	Each such insertion increases the collision counter by one. Rejected duplicate IDs do not increase the collision count.

Name: Arumit Kumar

Description:
CampusGraph: represents the campus buildings and the walkways connecting them. It loads building and connection information from input files, displays the graph, calculates graph statistics, and performs BFS to determine which buildings are reachable from a starting building.

Graph Data Structures:

1. `vector<string> names`
   - Stores the names of all campus buildings.
   - Each building is assigned an index based on its position in the vector.

2. `vector<vector<int>> adjList`
   - Stores the connections between buildings using their integer indexes.
   - Each inner vector contains the indexes of buildings directly connected to that building.

Graph Representation: Adjacency List

The project uses an adjacency list implemented with a vector of vectors.

Each building represents a vertex, and each walkway between two buildings represents an edge.

The graph is undirected, meaning that if Building A is connected to Building B, Building B is also connected to Building A. Therefore, each connection is stored in both buildings' adjacency lists.

This representation was chosen because a campus graph generally has fewer connections than the number of all possible connections between buildings. An adjacency list avoids storing unnecessary connections and makes it easy to access the neighbors of a building.

Graph Vertices and Edges:

- Vertices (V): Represent campus buildings, such as Library, Gym, and Science Building.
- Edges (E): Represent walkways connecting two buildings.
- The graph is undirected and unweighted. Each edge represents a direct connection between two buildings, without assigning a distance or cost.

Graph Algorithms:

Breadth-First Search (BFS):

The project uses Breadth-First Search to determine which buildings can be reached from a selected starting building.

BFS uses:
- Queue: Processes buildings in First-In, First-Out (FIFO) order.
- Visited vector (`status`): Keeps track of buildings that have already been visited.
- Distance vector (`distance`): Stores the number of connections from the starting building.

The BFS algorithm works as follows:

1. The user enters a starting building.
2. The program checks whether the building exists in the graph.
3. The starting building is marked as visited and assigned distance 0.
4. The program processes the queue and checks each building's neighboring buildings.
5. Unvisited neighbors are marked as visited, assigned a distance, and added to the queue.
6. The process continues until the queue is empty.
7. The program displays the reachable buildings and their distances.

The algorithm also handles isolated buildings and invalid starting building names.

Other Implemented Graph Operations:

- `loadBuildings()`: Loads building names from the input file and rejects duplicate building names.
- `loadConnections()`: Loads connections and rejects malformed records, unknown buildings, self-connections, and duplicate or reversed connections.
- `findNode()`: Searches for a building using case-insensitive name comparison.
- `addEdge()`: Adds an undirected connection between two buildings.
- `viewBuildingsandConnection()`: Displays buildings and their neighboring buildings.
- `generateGraphStats()`: Displays the total number of buildings, total connections, and degree of each building.

Time Complexity:

Let:
- V = Number of vertices (buildings).
- E = Number of edges (connections).

Main Operations:

- `findNode()`: O(V)
- `getOrAddNode()`: O(V)
- `addEdge()`: O(V)
- `loadBuildings()`: O(V²), because each new building is checked against previously loaded buildings to detect duplicates.
- `loadConnections()`: O(E × V) in the worst case, because building names are searched for each connection.
- `viewBuildingsandConnection()`: O(V + E), because the program visits every building and its adjacency list.
- `generateGraphStats()`: O(V + E), because it calculates the total connections by examining the adjacency lists.

BFS Time Complexity:
- O(V + E), because BFS visits each reachable building and examines its connections.

Graph Space Complexity:

- O(V + E), where V is the number of buildings and E is the number of connections.
- The `names` vector stores V building names.
- The adjacency list stores 2E entries because every undirected connection is stored in both directions.
- BFS requires O(V) additional space for the visited vector, distance vector, and queue.

Design Justification:

An adjacency list was selected because it is memory-efficient for a campus graph where buildings usually connect to only a small number of other buildings.

Compared with an adjacency matrix, an adjacency list does not require storing a V × V matrix containing mostly empty connections.

Using `vector<string>` allows the program to store readable building names, while `vector<vector<int>>` allows connections to be stored using integer indexes.

This design also makes it straightforward to add connections, display neighboring buildings, calculate graph statistics, and perform BFS.

Name: Vic Scorgie

Description: 

Tree Class: DepartmentTree class manages the campus departments and stores the names of their relationships within the hierarchy

Tree Structure: Implemented a general tree where each DepartmentNode stores a department name, a pointer to its parent node, and a vector of pointers to its child nodes. Allows departments to have multiple child departments.

Insertion and Search Functions: addDepartment() adds a new department under existing parent nodes and checks for duplicate or invalid names. Implemented searchDepartment() to find departments and display their parent, number of direct children, and depth. 

Tree Traversal: Implemented displayHierarchy() to display the department structure with indentation and preorderTraversal() to visit each parent before the children. Utilizes a stack for iterative traversal.

Time Complexity: 
-> isEmpty(): O(1)
-> loadFromFile(): O(n²)
-> addDepartment(): O(n)
-> searchDepartment(): O(n)
-> displayHierarchy(): O(n)
-> preorderTraversal(): O(n)
-> Destructor: O(n)

Space Complexity: O(n) for storing the tree. The traversal and search operations can use additional O(n) space for their stacks

Design Justification: A general tree design was chosen because campus departments can naturally form a hierarchy, where one department can have multiple subdepartments. Using a vector of child pointers allows the tree to support any number of children without a fixed limit.
